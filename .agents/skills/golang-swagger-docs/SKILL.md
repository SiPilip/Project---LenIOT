# Go Backend Swagger/OpenAPI Documentation

Keeps Swagger annotations perfectly in sync with actual Go handler code, using
`swaggo/swag` as the annotation-to-OpenAPI generator. The core rule this skill
enforces: **no request or response shape changes without a matching Swagger
doc change, verified by regeneration — not by eyeballing.**

## The non-negotiable rule

Whenever a change touches any of the following, Swagger docs are part of the
change, not an afterthought:

- A handler function signature or route registration
- A request struct (query params, path params, body, headers)
- A response struct (success body, error body, status codes)
- Auth/security requirements on an endpoint

**Never mark a handler change complete without running the sync check in
"Verification workflow" below.** If the check fails or can't be run, say so
explicitly instead of silently skipping it.

## Stack assumptions (adjust if the project differs)

- Generator: `github.com/swaggo/swag` (`swag init`)
- Framework glue: `github.com/swaggo/gin-swagger` + `github.com/swaggo/files`
  for Gin (swap for `echo-swagger`, etc. if the project uses a different
  router — annotation syntax is identical, only the serving middleware
  changes)
- Auth: session-cookie based auth is common in Go+Gin backends here — document
  it with a `cookie`-type security definition (see below), not bearer/JWT,
  unless the project actually uses a token header.

## 1. One-time setup

```bash
go install github.com/swaggo/swag/cmd/swag@latest
go get -u github.com/swaggo/gin-swagger
go get -u github.com/swaggo/files
```

`main.go` needs exactly one general API annotation block (above `func main()`)
and the route to serve the UI + spec:

```go
// @title           <Service Name> API
// @version         1.0
// @description     <one or two sentence description>
// @BasePath        /api/v1

// @securityDefinitions.apikey CookieAuth
// @in                          cookie
// @name                        session_id
// @description                 httpOnly session cookie set on login

package main

import (
	swaggerFiles "github.com/swaggo/files"
	ginSwagger "github.com/swaggo/gin-swagger"
	_ "yourmodule/docs" // generated by `swag init` — must be imported for side effects
)

func main() {
	r := gin.Default()
	r.GET("/swagger/*any", ginSwagger.WrapHandler(swaggerFiles.Handler))
	// ...routes
}
```

Run `swag init` once to generate the `docs/` package, then commit `docs/`
(or add it to CI generation — see verification workflow).

## 2. Annotating a handler

Every exported handler that's wired to a route gets a comment block directly
above it. Use this as the template and fill every field — don't omit
`@Success`/`@Failure` even for "obvious" endpoints:

```go
// CreateLoan godoc
// @Summary      Create a new loan application
// @Description  Creates a KPR loan application for the authenticated user
// @Tags         loans
// @Accept       json
// @Produce      json
// @Param        request body     dto.CreateLoanRequest  true  "Loan application payload"
// @Success      201  {object}  dto.LoanResponse
// @Failure      400  {object}  dto.ErrorResponse  "validation error"
// @Failure      401  {object}  dto.ErrorResponse  "not authenticated"
// @Failure      500  {object}  dto.ErrorResponse
// @Security     CookieAuth
// @Router       /loans [post]
func (h *LoanHandler) CreateLoan(c *gin.Context) {
	...
}
```

Rules for this block:

- **`@Param`**: one line per request input. Body params use
  `body dto.XRequest true "..."`; path params use
  `path string true "user id"`; query params use
  `query int false "page number"`. Every field the handler actually reads
  from the request must have a corresponding `@Param` (directly, or via the
  referenced struct's own field tags — see below).
- **`@Success` / `@Failure`**: one line per distinct status code the handler
  can actually return. Grep the handler body for every `c.JSON(`,
  `c.Status(`, `c.AbortWithStatusJSON(` call and make sure each status code
  is represented. If the handler adds a new error branch, add a `@Failure`
  line in the same change.
- **`@Security`**: present on every endpoint behind auth middleware, absent
  on public ones. If the route is registered under an authenticated router
  group, it needs `@Security CookieAuth` (or whatever the project's
  security definition is named) even if the handler itself doesn't check
  auth directly.
- **`@Router`**: must match the actual path and HTTP method passed to
  `r.POST(...)` / `r.GET(...)` etc., including the group prefix. If routes
  are registered on a group (`v1 := r.Group("/api/v1")`), the `@Router` path
  is relative to `@BasePath`, not the group — write the full path from
  `/api/v1` down and mentally cross-check it against the route registration.

## 3. Annotating request/response structs

Swaggo reads struct tags, not a second copy of the schema — keep it that way
so there's only one source of truth:

```go
type CreateLoanRequest struct {
	Amount      int64  `json:"amount" binding:"required,min=1000000" example:"50000000"`
	TenorMonths int    `json:"tenor_months" binding:"required,min=12,max=360" example:"180"`
	PropertyID  string `json:"property_id" binding:"required,uuid" example:"c1a2..."`
}

type LoanResponse struct {
	ID          string    `json:"id" example:"9f8e..."`
	Status      string    `json:"status" example:"pending_review" enums:"pending_review,approved,rejected"`
	CreatedAt   time.Time `json:"created_at"`
}

type ErrorResponse struct {
	Code    string `json:"code" example:"VALIDATION_ERROR"`
	Message string `json:"message" example:"amount must be at least 1,000,000"`
}
```

- Every field that has a `json` tag and is actually read/written by the
  handler needs an `example` tag (or a real zero-value that's self-evident,
  like `bool`). Swagger UI without examples is worse than no swagger UI.
- If a field has `binding:"required"` (Gin/validator), that's what drives
  swaggo's `required` in the generated schema — don't duplicate it as a
  comment.
- Use `enums:"a,b,c"` for any field that's effectively a closed set (status
  fields, roles, types) — this is the single highest-value annotation for
  catching integration bugs early, use it liberally.
- Keep one struct per request/response shape. Don't reuse a "generic" struct
  across endpoints just to avoid writing a new one — it makes the generated
  docs lie about which fields a given endpoint actually needs.

## 4. Verification workflow (run this every time, not just at the end)

This is the actual enforcement mechanism — annotations that don't regenerate
cleanly, or that produce a diff nobody reviewed, are worse than no
annotations, because they actively mislead API consumers.

```bash
# 1. Regenerate from current source
swag init -g main.go --parseDependency --parseInternal

# 2. Confirm it succeeded — swag exits non-zero and prints the offending
#    file/line on a malformed annotation. Fix and rerun before moving on.

# 3. Diff against what's committed
git diff --stat docs/

# 4. Read the diff, not just the stat. Every new/changed field, status code,
#    or route in docs/swagger.json should map to a request/response change
#    you just made. An unexpected diff means either:
#      - stale docs from a previous change that was never regenerated, or
#      - the handler is doing something the annotations don't describe
```

Treat a non-empty, unexplained diff the same as a failing test: don't
consider the handler change done until the diff is either committed
(expected) or investigated (unexpected).

Optional: `scripts/check_swagger_sync.sh` in this skill folder wraps steps
1–3 for CI or a pre-commit hook — it fails the build if `swag init` produces
a diff that wasn't committed.

## 5. Common pitfalls (check these explicitly)

- **New field added to a struct, no `example` tag** → docs render an empty
  value; add it in the same commit.
- **New error branch (`c.JSON(409, ...)`), no matching `@Failure` line** →
  grep the handler for every JSON-writing call and cross-check against the
  annotation block every time a branch is added or removed.
- **Route moved to/from an authenticated group without updating `@Security`**
  → this is the highest-risk drift because it makes docs claim an endpoint
  is public (or protected) when it isn't.
- **Nested/embedded structs** (`type X struct { Y }`) — swaggo needs
  `--parseDependency` (and often `--parseInternal`) to resolve these across
  packages; if a nested type shows up as an empty `{}` in the generated
  spec, that's the fix, not restructuring the Go types.
- **Pagination/list endpoints** — document the wrapper, not just the item:

  ```go
  // @Success 200 {object} dto.PaginatedResponse{data=[]dto.LoanResponse}
  ```

- **File upload endpoints** — use `@Accept multipart/form-data` and
  `@Param file formData file true "..."`.
- **`docs/` not committed / not regenerated in CI** → the served
  `/swagger/index.html` silently goes stale. Regeneration must be a build
  step, not a manual "someone remembers to run swag init" step.

## 6. When asked to "add an endpoint" or "change a field"

Do the annotation work in the same pass as the code, not as a follow-up:

1. Write/modify the handler, request struct, response struct.
2. Write/update the `godoc` annotation block immediately above the handler.
3. Run the verification workflow (section 4).
4. Report the diff summary to the user as part of the change, e.g. "added
   `POST /loans`, regenerated docs — new `dto.CreateLoanRequest` and
   `dto.LoanResponse` schemas now in `docs/swagger.json`."

If `swag` isn't installed or the sandbox has no network access to install
it, say so plainly rather than silently writing annotations that were never
validated against the generator.
